## Назначение

Эта папка содержит **детальные технические спецификации**, правовые и операционные шаблоны, а также материалы для запуска пилота. Теперь это не просто набор приложений, а **операционный слой ТЭО**, который поддерживает PTRL-логику, Node Zero, Evidence Matrix, MVP-право и resident protocol.

## Главная функция библиотеки в версии 6.0

Приложения нужны, чтобы каждая сильная идея из ТЭО могла быть:

- разложена по уровням готовности;
- привязана к конкретному узлу пилота;
- подтверждена документом, спецификацией, сметой, KPI или телеметрией;
- переведена в шаблон договора, процесса или паспорта объекта.

## Рекомендация по структуре

**Вопрос:** Стоит ли включать эти технологии в развернутом виде в основное тело ТЭО?
**Ответ:** **Нет, рекомендуется оставить их в Приложениях.**

### Аргументация

1. **Фокус внимания:** Основной документ (Разделы 1-12) читают инвесторы и чиновники. Им важны: *Деньги, Риски, Сроки, Право*. Технические детали перегружают.
2. **Модульность:** Технологии меняются быстрее экономической модели. Приложения можно обновлять автономно.
3. **Уровни доступа:**
    - *Level 1 (ТЭО, Разделы 1-12):* Стратегия и Экономика.
    - *Level 2 (Приложения — эта папка):* Инженерные решения, спецификации, стоимость, KPI-паспорта, процессы, MVP-право и шаблоны.

## Сквозная логика приложений

| Опорный принцип | Что это значит для приложений |
| :--- | :--- |
| **PTRL** | Любая технология описывается как стадийная система: база, телеметрия, сервис, оптимизация, масштаб |
| **Node Zero** | У каждой категории есть минимальная пилотная конфигурация, которую реально развернуть первой |
| **Evidence Matrix** | По каждому сильному тезису должен быть проверяемый артефакт: КП, ТУ, договор, фото, дашборд, акт |
| **MVP-право** | Обязательный правовой контур пилота отделен от сложных опций масштаба |
| **Resident Protocol** | Резидент рассматривается как участник управляемой среды с понятным онбордингом, правилами доступа и privacy |

## Принципы отбора технологий (v6.0)

- ✅ **Проверенные временем** — приоритет серийным, сертифицированным решениям с историей эксплуатации ≥5 лет в РФ.
- ✅ **Климатическая адаптация** — все решения проверены на работоспособность при температурах −35…+35°C, снеговых нагрузках до 240 кг/м², весенней распутице.
- ✅ **Доступные поставщики** — указаны конкретные российские производители и дистрибьюторы.
- ✅ **Прозрачная экономика** — для каждой технологии указаны CAPEX, OPEX, сроки окупаемости, ROI-таблицы.
- ✅ **Экологические паспорта** — энергоэффективность, экологичность материалов для каждого сектора.
- ✅ **Node Zero ready** — у технологии должен быть минимальный пилотный сценарий внедрения.
- ✅ **Proof ready** — у технологии должен быть owner и подтверждаемый артефакт для Evidence Matrix.
- ⚠️ **Инновации — осторожно** — экспериментальные технологии выделены в поздние уровни PTRL и не считаются обязательными для первого запуска.

## Практический режим применения: ONN

Если в качестве живого полигона используется анонимизированный кейс ПРП ONN, библиотека применяется так:

1. `01_Транспорт_и_Логистика.md` — для реестра техники, зимнего протокола и сервисного выезда.
2. `02_Строительство_и_Архитектура.md` — для лёгких модульных и рекреационных сценариев без перегруза капитальным строительством.
3. `03_Энергетика_и_ЖКХ.md` — для базового учёта, резервирования и журналов инцидентов, а не для преждевременной микросети.
4. `04_Агротехнологии_и_Производство.md` — для одного агро-пилота с понятной юнит-экономикой и owner.
5. `05_Управление_и_Цифра.md` — для helpdesk, бронирования, role matrix и минимальной цифровой прозрачности.

Главное правило: ONN — это **brownfield pre-Node Zero**, поэтому приложения должны помогать запускать первые работающие сервисы, а не превращать живой поселок в перегруженную демонстрацию технологий.
